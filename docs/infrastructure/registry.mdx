---
title: "Google Artifact Registry"
description: "Provision and operate the required user-owned image registry."
---

Techulus Cloud requires a user-owned [Google Artifact Registry](https://cloud.google.com/artifact-registry/docs) (GAR) Docker repository for images built from GitHub sources. Techulus does not provision or own the repository.

Agents push and pull image data directly. The control plane uses the GAR API only to manage protection tags; GAR cleanup policies exclusively delete image versions and reclaim blobs. User-supplied images can still use credentials configured under **Settings → Registries**.

## Image layout

Each source-backed service has one GAR package:

```text
<location>-docker.pkg.dev/<gcp-project>/<repository>/<techulus-project-id>/<service-id>:revision-<revision-id>
```

The final multi-platform version receives both its immutable `revision-*` tag and a deterministic `protected-revision-*` tag before rollout begins. A GAR failure at this boundary prevents deployment of an unprotected image.

## Provision GAR

### Recommended: setup helper

Run [`deployment/setup-gar.sh`](https://github.com/techulus/cloud/blob/main/deployment/setup-gar.sh) from [Google Cloud Shell](https://cloud.google.com/shell/docs), opened from the Google Cloud Console. Cloud Shell already has Bash, Git, and an authenticated `gcloud` CLI. A trusted admin workstation with [Google Cloud CLI](https://cloud.google.com/sdk/docs/install) installed and authenticated also works. Do not run the helper from the Techulus control plane or agent.

The operator needs permission to enable APIs, administer Artifact Registry repositories and their IAM policies, create service accounts, and create service-account keys. The predefined roles that supply these permissions are Service Usage Admin, Artifact Registry Administrator, Service Account Admin, and Service Account Key Admin, or custom roles with the equivalent permissions.

```bash
git clone https://github.com/techulus/cloud.git
cd cloud

./deployment/setup-gar.sh \
  --project google-project-id \
  --location us-central1 \
  --repository techulus-images
```

The helper displays the active Google account and complete repository target, then requires the exact project ID before making changes. It creates or reuses the repository and dedicated service accounts, applies repository-scoped access, and creates two fresh service-account keys. Existing keys are never changed. If no cleanup policies exist, it also installs the tracked policy in dry-run mode; it never enables deletion.

The three required values are written to `$HOME/techulus-gar.env` with mode 600 and are never printed. Cloud Shell's home directory persists between sessions unless you use [ephemeral mode](https://cloud.google.com/shell/docs/use-cloud-shell#ephemeral_mode). Securely transfer the values into the Techulus deployment `.env` or installer, then delete the generated file from Cloud Shell:

```bash
rm "$HOME/techulus-gar.env"
```

Each confirmed rerun creates fresh keys, so do not rerun the helper merely to recover a deleted output file. Google does not allow an existing private key to be downloaded again.

Service-account key creation can be prohibited by the `iam.disableServiceAccountKeyCreation` organization policy, which is enforced by default for many organizations created after May 3, 2024. The helper reports this failure but does not weaken organization policy; an organization administrator must approve and configure an exemption before Techulus can use static GAR credentials.

### Manual setup

As an auditable fallback, install and authenticate `gcloud`, choose a GCP project and location, and enable Artifact Registry and IAM:

```bash
export GAR_PROJECT_ID=google-project-id
export GAR_LOCATION=us-central1
export GAR_REPOSITORY_ID=techulus-images

gcloud services enable \
  artifactregistry.googleapis.com \
  iam.googleapis.com \
  --project="$GAR_PROJECT_ID"

gcloud artifacts repositories create "$GAR_REPOSITORY_ID" \
  --project="$GAR_PROJECT_ID" \
  --location="$GAR_LOCATION" \
  --repository-format=docker \
  --description="Techulus Cloud source images"
```

Create two dedicated service accounts. The agent account can upload and download artifacts. The control-plane account uses its Repository Administrator role to create/delete protection tags, not to delete images or packages. It cannot create or reconfigure repositories.

```bash
export GAR_AGENT_SA="techulus-agent@${GAR_PROJECT_ID}.iam.gserviceaccount.com"
export GAR_ADMIN_SA="techulus-control-plane@${GAR_PROJECT_ID}.iam.gserviceaccount.com"

gcloud iam service-accounts create techulus-agent \
  --project="$GAR_PROJECT_ID" \
  --display-name="Techulus agents"
gcloud iam service-accounts create techulus-control-plane \
  --project="$GAR_PROJECT_ID" \
  --display-name="Techulus control plane"

gcloud artifacts repositories add-iam-policy-binding "$GAR_REPOSITORY_ID" \
  --project="$GAR_PROJECT_ID" \
  --location="$GAR_LOCATION" \
  --member="serviceAccount:${GAR_AGENT_SA}" \
  --role="roles/artifactregistry.writer"

gcloud artifacts repositories add-iam-policy-binding "$GAR_REPOSITORY_ID" \
  --project="$GAR_PROJECT_ID" \
  --location="$GAR_LOCATION" \
  --member="serviceAccount:${GAR_ADMIN_SA}" \
  --role="roles/artifactregistry.repoAdmin"
```

Create JSON keys with private file permissions and write each complete document to the same three-value environment file produced by the helper:

```bash
umask 077
gcloud iam service-accounts keys create agent-key.json \
  --iam-account="$GAR_AGENT_SA" --project="$GAR_PROJECT_ID"
gcloud iam service-accounts keys create admin-key.json \
  --iam-account="$GAR_ADMIN_SA" --project="$GAR_PROJECT_ID"

{
  printf 'GAR_REPOSITORY=%s-docker.pkg.dev/%s/%s\n' \
    "$GAR_LOCATION" "$GAR_PROJECT_ID" "$GAR_REPOSITORY_ID"
  printf 'GAR_AGENT_KEY_BASE64=%s\n' \
    "$(base64 < agent-key.json | tr -d '\n')"
  printf 'GAR_ADMIN_KEY_BASE64=%s\n' \
    "$(base64 < admin-key.json | tr -d '\n')"
} > "$HOME/techulus-gar.env"
chmod 600 "$HOME/techulus-gar.env"

rm -f agent-key.json admin-key.json
```

Treat `$HOME/techulus-gar.env` as the private key: securely transfer its values into Techulus and delete it after use. Google does not allow either private JSON key to be downloaded again.

Configure every control-plane web replica:

```env
GAR_REPOSITORY=us-central1-docker.pkg.dev/google-project-id/techulus-images
GAR_AGENT_KEY_BASE64=<base64 Writer service-account JSON>
GAR_ADMIN_KEY_BASE64=<base64 Repository Administrator service-account JSON>
```

`GAR_REPOSITORY` must not include a scheme, image path, tag, or digest. The health endpoint returns 503 when any mandatory GAR value is missing or malformed.

## Agent authentication

The control plane includes exactly one system GAR credential in each agent's encrypted registry bundle. It uses GAR's `_json_key_base64` Docker login and the Writer key. BuildKit uses it to push platform images and manifests; Podman uses it to pull deployments. TLS verification is always enabled.

The Repository Administrator key stays in the control plane and is never sent to agents. Static repository-scoped keys are intentional: an agent can lease one credential snapshot for a build lasting up to 120 minutes, while GAR OAuth access tokens expire after 60 minutes.

## Cleanup policy

The tracked [`deployment/gar-cleanup-policy.json`](https://github.com/techulus/cloud/blob/main/deployment/gar-cleanup-policy.json) defines two repository policies:

- keep every version carrying a `protected-` tag;
- delete tagged or untagged versions older than 30 days when no keep policy matches.

Keep policies win over delete policies. For Docker images, GAR does not delete child manifests while a retained parent manifest references them.

Do not retain an unconditional newest-ten-versions Keep policy: it would preserve deleted-service images indefinitely. Techulus implements retention of the newest 10 completed rollouts through protection tags instead. On an existing repository, review and apply the tracked policy, removing any blanket recent-version Keep rule. The setup helper preserves existing policies; upgrading Techulus does not change them automatically.

The operator applying policies needs Artifact Registry Administrator permissions. The helper applies this file in dry-run mode when the repository has no existing policies. For manual setup, or after reviewing policies already present on an existing repository, apply the file in dry-run mode explicitly:

```bash
gcloud artifacts repositories set-cleanup-policies "$GAR_REPOSITORY_ID" \
  --project="$GAR_PROJECT_ID" \
  --location="$GAR_LOCATION" \
  --policy=deployment/gar-cleanup-policy.json \
  --dry-run
```

GAR evaluates cleanup asynchronously, generally within one day. Enable Artifact Registry Data Write audit logs, wait for a dry-run cycle, and inspect the proposed `BatchDeleteVersions` operations. When the keep/delete set is correct, activate deletion:

```bash
gcloud artifacts repositories set-cleanup-policies "$GAR_REPOSITORY_ID" \
  --project="$GAR_PROJECT_ID" \
  --location="$GAR_LOCATION" \
  --policy=deployment/gar-cleanup-policy.json \
  --no-dry-run
```

Techulus retains protection for active deployments, queued or in-progress work, and the newest 10 completed rollouts. Its daily job removes only the `protected-revision-*` tag after a locked final eligibility check. GAR then owns version deletion and physical blob reclamation. The 30-day condition is measured from upload time, not from when Techulus removes protection.

Deleting a stateless service or preview releases all its historical GitHub-image protection tags before removing its database records, including images built before GitHub was disconnected. A deleted stateful service retains protection through the seven-day restore window; expiry purge then releases it. Failed tag releases leave the service records available for retry, and late build callbacks cannot recreate protection after deletion.

Techulus never directly deletes GAR packages or versions. Unprotected images already older than 30 days become eligible for the next cleanup cycle; younger images remain until they reach that age. This is not a new 30-day grace period from service deletion. Cleanup must be activated explicitly after dry-run review; dry-run alone reclaims no storage. Empty package metadata may remain after GAR removes its versions.

## Upgrading from the bundled registry

This is a clean beta cutover. Techulus does not copy old images or rewrite persisted image references. Configure GAR and both keys before upgrading. Existing source-built revisions then point to an unavailable old registry and every source-backed service must be rebuilt before it can deploy from GAR.

The upgrade removes the old registry container but deliberately leaves its Docker volume. After the upgrade is verified and you no longer need rollback data, inspect and explicitly remove the orphaned volume:

```bash
docker volume ls --filter name=registry-data
docker volume rm <exact-volume-name>
```

Volume deletion is irreversible and is never performed automatically.

## Global custom registries

Administrators can add credentials for user-supplied private images under **Settings → Registries**. A host, including an explicit port when needed, is globally unique and cannot include a scheme or path. The GAR system host is reserved.

Changes are queued for every registered agent, including offline agents. Entries cannot be edited; delete and recreate one to change its username, password, or TLS setting. Use pull-only robot or service-account credentials where possible. Passwords are write-only in the UI, and an actual agent pull remains the authoritative availability check.
